Problem

Large RESTlet payloads (e.g. File Cabinet uploads through cp_file_cabinet_rl) were believed to be capped at ~700KB binary / ~1MB text because --data was assumed to be inline-only, bounded by the shell's ARG_MAX. That belief is wrong: restlet call --data already routes through the shared read_data_arg helper (cli.rs:895), which supports @path (read from file) and - (stdin) — the same forms the record commands document. Nothing in restlet call's help or examples says so, and downstream docs propagated the false ceiling.

Empirical findings (sb2, 2026-08-11)

ProbeResult
2.5MB text upload via --data @fileCreated; downloaded byte-identical
9.9MB text upload (just under the RESTlet's 10MB decoded cap)Created, size 9,900,000
7MB binary upload (9.3MB base64 JSON body)Created; downloaded byte-identical
11MB body (over the RESTlet cap)NetSuite accepted the request; cp_file_cabinet_rl's own cap error came back — the per-RESTlet cap is the binding limit, platform ceiling ≥ 11MB

Decisions

No new flag. --data-file is rejected as a redundant synonym; @path is the repo's established convention. This change is documentation and help text only — zero behavior change.
Scope: restlet call only in the CLI. raw/job submit use the same helper and inherit the behavior, but their help is untouched (the shipped skill's generic "Data input" line covers the forms).

Changes

1. src/cli.rs — RestletAction::Call's data arg gains a doc comment (currently none):

/// JSON body for POST/PUT: inline JSON, @path to read it from a file, or - for stdin.
/// Use @file for large payloads — inline args are capped by the shell's ARG_MAX (~1MB).
#[arg(long)]
data: Option<String>,

and the subcommand's after_help gains one example line:

netsuite-cli restlet call --script 482 --deploy 1 --method PUT --data @payload.json

2. skills/netsuite-cli/SKILL.md — the RESTlet row / section notes that --data accepts the same three input forms everywhere it appears (record, raw, job submit, restlet call), and that payload size limits are per-RESTlet, not CLI-side (platform accepts ≥11MB request bodies). No CP-specific content — the documentation split stands.

3. Out-of-repo (not part of this PR): the local cp-file-cabinet skill's size-limits section replaces the ARG_MAX claim with the verified limits (10MB decoded cap enforced by the RESTlet; --data @file for anything large; 9.9MB text / 7MB binary verified), and the paired memory file gets a one-line correction.

Testing & rollout

  • read_data_arg's @file/stdin behavior is already unit-tested (commands/mod.rs tests). New tests: none needed for a docs change; the plan checks whether any help-snapshot tests exist and updates them if so.
  • cargo build + cargo test green; patch version bump per repo convention.
  • PR against main, then pr-review-loop; local skill/memory edits after merge.

Out of scope

  • A --data-file flag; any behavior change to read_data_arg; raw/job-submit help text; chunked-transfer support (the 10MB per-RESTlet cap makes it moot for File Cabinet).
